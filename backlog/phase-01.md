## 🎯 배경 및 목표

### 현재 상황

책을 읽고 나면 "내가 맞게 읽었나, 남들은 어떻게 읽었나"가 궁금하다. 독서 모임에 가면 다양한 의견과 작품 배경을 들을 수 있지만, 시간과 장소의 제약이 크고 모임이 끝나면 대화가 남지 않는다.

기존 서비스는 이 자리를 비워 두고 있다. 독서 앱은 서재 관리와 리뷰 공유에 집중하고, AI 독서 서비스는 책 본문을 가지고 읽는 중의 질문에 답한다 (`docs/goals.md` §참고한 서비스). 읽은 뒤에 독자가 먼저 쓰고 그 글을 실제 평가에 비춰 보는 서비스는 찾지 못했다.

이 phase 는 다른 사용자 없이도 그 경험을 얻을 수 있는 1인용 제품을 만든다. 지금 넘어야 할 상대는 일반 AI 채팅이다. 아직 저장소에는 확정된 아키텍처와 코드가 없다.

### 목표 (Goal)

만든 사람 본인이 로컬 docker 환경에서 책 한 권에 대해 다음 흐름을 끝까지 수행할 수 있다.

1. 책 등록
2. 내 해석 먼저 쓰기
3. 내 해석과 맞닿는 배경과 작가의 의도 보기 (출처 포함)
4. 실제 사람들의 다른 시선 보기 (출처 포함, AI 가 만든 해석은 표시)
5. 비교 보기 — 책과 어긋나는 곳, 다르게 읽은 곳. 여기까지 보면 모임이 저장된다
6. (선택) 시선 하나를 골라 토론하고, 달라진 생각을 노트로 적기

독자가 반드시 써야 하는 것은 2번 한 번이다. 대상은 소설이다 (비문학은 구조만 열어 둔다).

### 성공 기준 (Success Criteria) — 정량 우선

실제로 읽은 소설 5권으로 잰다.

1. 5권 모두 1~5 흐름을 끝까지 수행한다.
2. 5권 중 4권 이상에서, 모임 끝의 한 번 고르기 질문에 "새로 알게 된 것이 있었다" 또는 "생각이 달라졌다"를 고른다.
3. 5권 중 4권 이상에서, 같은 책에 대해 내 해석을 일반 AI 채팅에 붙여 넣고 물어본 결과보다 낫다고 스스로 평가한다.
4. 5권의 배경과 시선에 표시된 모든 사실과 인용에 출처가 붙어 있고, 직접 열어 봤을 때 출처가 그 내용을 담고 있지 않거나 틀린 경우가 0건이다.
5. 내 해석을 저장하기 전에는 다른 시선과 비교가 화면과 API 어디에서도 노출되지 않는다 (자동 테스트로 검증).
6. `docker compose up` 한 번으로 웹 앱과 DB 가 뜨고, 재시작 후에도 데이터가 유지된다. 작업 프로세스는 호스트에서 명령 하나(`pnpm worker`)로 띄운다 (2026-11-17 고침: CLI 로그인을 호스트의 것으로 쓰기 때문).

### spec-01-01 — 수동 실험

- **요점**: 코드를 만들기 전에, 읽은 책 2권(소설 1, 비문학 1)으로 전체 흐름을 AI 대화에서 손으로 돌려 본다 (코드 없음, 문서만).
- **방향성**: 단계별 프롬프트 초안을 만들고 사용자가 직접 수행한다. 같은 책을 "내 해석을 붙여 넣고 다른 해석을 묻는" 일반 채팅과 비교한다. 결과와 프롬프트를 `docs/experiments/` 에 기록하고, `docs/goals.md` 열린 질문 세 가지에 답한다.
  1. 소설과 비문학을 둘 다 다룰 것인가, 흐름과 표현을 어떻게 나눌 것인가
  2. 배경을 내 해석을 쓰기 전에도 보여줄 것인가
  3. 책 본문 없이 "책과 어긋나는 곳"을 믿을 만하게 짚을 수 있는가

  그 밖에 확인할 것: 실제 평론과 독자 반응이 검색으로 충분히 찾아지는가 (한국어 책 포함), 출처가 실제로 그 내용을 담고 있는가, AI 가 만든 해석이 서로 비슷해지지 않는가.
- **참조**:
  - `docs/goals.md` §위치, §열린 질문, §참고한 서비스
- **연관 모듈**: `docs/experiments/`

### spec-01-02 — 아키텍처 결정

- **요점**: 구현 전에 정해야 할 구조적 결정을 ADR 로 확정한다 (코드 없음, 문서만).
- **방향성**: 수동 실험 결과를 근거로 아래 다섯 가지를 각각 선택지와 근거를 비교해 ADR 로 남긴다. 결과에 따라 이후 spec 의 범위와 순서를 재검증한다.
  1. 앱 구조 — 단일 웹 앱인가, 프론트와 백엔드 분리인가. 언어와 프레임워크 포함
  2. 데이터 모델 — "시선"을 출처가 있는 실제 시선, AI 가 만든 해석, (이후) inkle 독자의 해석을 모두 담는 하나의 개념으로 둘 것인가. 글쓴이 구분(나 / AI / 외부 사람)을 모든 문장 단위 자료에 어떻게 남길 것인가
  3. 사용자 식별 — 인증이 없는 지금도 모든 데이터에 사용자 식별자를 둘 것인가
  4. LLM 근거 — 배경과 실제 시선을 찾고 확인하는 방식 (웹 검색, 출처 표기, 출처가 내용을 담고 있는지 검증)
  5. 원본과 파생물 — 대화·노트를 원본으로 보존하고 이후 위키를 파생물로 만들 수 있는 저장 구조
- **참조**:
  - `docs/goals.md` §원칙, §열린 질문
  - spec-01-01 의 실험 기록
- **결과** (2026-11-17): ADR-001 ~ 005 (`docs/decisions/README.md`). LLM 은 Claude API 대신 Claude Code CLI 를 구독으로 쓴다 (사용자 결정). 이에 따라 아래 spec 의 범위를 고치고 "자료 수집"을 spec-01-06 으로 새로 넣었다 (이후 번호가 하나씩 밀림).
- **연관 모듈**: `docs/decisions/`

### spec-01-03 — 프로젝트 뼈대와 로컬 환경

- **요점**: 확정된 아키텍처대로 빈 프로젝트, docker 환경(웹 앱, 작업 프로세스, DB), 테스트 실행기를 갖추고, ADR-004 의 가정을 실제로 확인한다.
- **방향성**:
  - **가장 먼저 ADR-004 의 "검증이 필요한 가정" 네 가지를 돌려 본다.** 컨테이너 안에서 CLI 가 구독 토큰으로 동작하는가, 웹 검색만 켜고 쓸 수 있는가, 결과 형식이 지켜지는가, 한국어 페이지의 본문을 글자로 뽑을 수 있는가. 틀린 가정이 있으면 멈추고 ADR 을 고친다.
  - `docker compose up` 으로 세 컨테이너가 뜨고, 테스트와 lint 가 한 명령으로 돈다. `sdd config precheck` 에 등록한다.
  - 작업 대기열 테이블과 빈 작업 하나가 처리되는 것까지 만든다 (ADR-001). 로컬 사용자 한 명을 미리 만든다 (ADR-003).
  - 워킹트리의 미커밋 Next.js 뼈대를 정리해 커밋한다. `@anthropic-ai/sdk` 의존성은 뺀다. ORM, 테스트 실행기, 마이그레이션 도구를 여기서 고른다.
  - CLI 토큰은 커밋하지 않는 환경 파일에 둔다 (저장소가 공개 상태).
- **참조**:
  - ADR-001, ADR-003, ADR-004
- **연관 모듈**: 프로젝트 루트, docker 설정

### spec-01-04 — 책 등록

- **요점**: 프론트 구조를 ADR 로 정한 뒤, 제목과 작가를 직접 입력해 책을 등록한다.
- **방향성**:
  - **첫 작업은 ADR-007 프론트 구조다** (사용자 요청, 2026-11-17). 제품 화면이 처음 생기는 spec 이므로 화면을 만들기 전에 아래를 선택지 비교와 함께 정한다. 이 판의 Next.js 문서(`node_modules` 안)를 확인하고 쓴다.
    1. 서버 컴포넌트와 클라이언트 컴포넌트의 경계 ("화면은 HTTP API 로만 자료를 읽고 쓴다"는 ADR-001 §4 를 지키는 방식)
    2. 자료 가져오기와 상태 관리 (수집 진행 상황의 주기적 조회, 모임 단계의 상태. 라이브러리를 쓸지 여부)
    3. HTTP API 응답의 타입을 서버와 화면이 공유하는 방식
    4. 화면 구조와 주소 체계 (책, 모임, 단계별 화면)
    5. 글쓰기 화면의 공통 규칙 (임시 저장, 이탈 방지). 내 해석 쓰기(spec-01-05)가 따른다
    6. 글쓴이(나 / AI / 외부 사람)와 출처의 종류를 화면에서 구분해 보여주는 공통 규칙 (ADR-002 §3)
    7. 폴더 구조, 스타일 방식, 컴포넌트 테스트 범위
  - 책 등록은 혼자 5권을 등록하는 단계이므로 직접 입력만 만든다. 책은 장르를 속성으로 가지며 지금은 소설만 고를 수 있다 (ADR-002). 외부 도서 검색 API 는 Icebox 로 미룬다 (`backlog/queue.md`). 서재 관리 기능으로 확장하지 않는다.
- **참조**:
  - `docs/goals.md` §하지 않을 것
  - ADR-001, ADR-002
- **연관 모듈**: 프론트 구조, 책 도메인

### spec-01-05 — 내 해석 쓰기

- **요점**: 책에 대한 내 해석을 질문 두세 개에 답하는 형태로 적어 저장한다.
- **방향성**: 저장 전에는 다른 시선과 비교를 볼 수 없도록 서버에서 강제한다 (성공 기준 5). 이 phase 에서는 소설용 질문만 만들고, 장르별로 질문을 바꿀 수 있는 구조로 둔다. 독자가 글을 쓰는 곳은 여기 한 번이므로 쓰기 쉽게 만드는 데 공을 들인다. 한 책에 대해 모임을 다시 열 수 있는 구조로 둔다. 내 해석은 원본이므로 고쳐 쓰면 새 판을 덧붙인다 (ADR-005). 모임을 시작하면 그 책의 자료 수집이 뒤에서 시작된다 (spec-01-06 이 생긴 뒤 연결).
- **참조**:
  - `docs/goals.md` §원칙 "먼저 쓰고, 그다음 본다"
- **연관 모듈**: 읽기 기록 도메인

### spec-01-06 — 자료 수집

- **요점**: 책 한 권의 배경과 시선을 찾고, 출처를 직접 열어 인용 문장을 대조한 뒤 책 단위로 저장한다. 화면은 없다.
- **방향성**: ADR-004 의 네 단계(찾기 → 가져오기 → 읽기 → 대조)를 작업 프로세스에서 구현한다. LLM 호출 경계를 만들고 Claude Code CLI 로 채운다. 대조를 통과한 인용이 없는 항목은 내주지 않는다. 출처의 종류와 "얼마나 흔한 읽기인가"를 저장한다. 테스트는 LLM 과 웹을 대역으로 바꿔 수행하고, 실제 호출은 책 한 권으로 수동 확인한다. 실험에서 쓴 두 책(『채식주의자』, 『노인과 바다』)으로 돌려 실험 기록과 비교한다.
- **참조**:
  - ADR-002, ADR-004, ADR-005
  - `docs/experiments/01-manual-flow/rehearsal.md`, `book-1.md`
- **연관 모듈**: LLM 연동, 작업 프로세스, 책 도메인

### spec-01-07 — 배경과 작가의 의도

- **요점**: 작품이 쓰인 시대, 작가의 삶과 의도 가운데 내 해석과 맞닿는 것을 골라 출처와 함께 보여준다.
- **방향성**: spec-01-06 이 모아 둔 배경 항목을 출처, 인용 문장, 출처의 종류와 함께 보여준다. 모은 자료가 없으면 "확인하지 못함"으로 표시한다. 일반적인 작품 소개로 끝나지 않도록 각 항목이 내 해석의 어느 부분과 맞닿는지(연결)를 독자별로 만들어 함께 보여준다. 내 해석을 쓴 뒤에만 보여준다. 수집이 끝나지 않았으면 진행 상황을 보여준다.
- **참조**:
  - `docs/goals.md` §원칙 "사실과 해석을 구분한다"
  - ADR-002, ADR-004, ADR-005
- **연관 모듈**: LLM 연동, 책 도메인

### spec-01-08 — 다른 시선과 비교

- **요점**: 실제 사람들의 시선을 출처와 함께 보여주고, 내 해석을 "책과 어긋나는 곳"과 "다르게 읽은 곳"으로 나눠 돌려준다.
- **방향성**:
  - 시선은 평론, 작가 인터뷰, 독자 반응에서 찾아 누가 어디서 한 말인지 붙인다. 실제 자료가 부족할 때만 AI 가 만든 해석을 덧붙이고 AI 가 쓴 것으로 표시한다.
  - "책과 어긋나는 곳"은 근거를 함께 제시한다. 출처로 확인된 것과 모델의 기억에 근거한 것을 구분하고, 기억에 근거한 것은 "확인 필요"로 낮춰 보여준다.
  - 찾은 시선이 다수 의견인지 드문 읽기인지 표시한다. 내 해석이 다수 의견과 다른 곳은 틀린 것이 아니라 드문 읽기로 보여준다.
  - 비교까지 보면 모임이 저장된다. 끝에 "새로 알게 된 것이 있었나 / 생각이 달라졌나"를 한 번 고르게 한다 (성공 기준 2).
  - "다르게 읽은 곳"에는 우열을 매기지 않는다.
  - AI 는 독자를 평가하지 않는다 (성향이나 수준에 대한 언급 없음).
- **참조**:
  - `docs/goals.md` §원칙 "오독은 근거와 함께 짚고…", "실제 사람의 시선이 먼저다", "AI 는 … 독자를 평가하지 않는다"
- **연관 모듈**: LLM 연동, 시선 도메인

### spec-01-09 — 토론

- **요점**: (선택 단계) 시선 하나를 골라 대화를 이어간다.
- **방향성**: 토론 상대는 고른 시선의 입장을 유지하며 쉽게 동의하지 않는다. 입장을 바꿀 때는 이유를 밝힌다. 대화 전체를 원본으로 저장한다 (이후 위키의 재료). 응답은 스트리밍으로 보여준다.
- **참조**:
  - `docs/goals.md` §원칙 "원본을 보존한다", §참고한 서비스 (연구)
- **연관 모듈**: LLM 연동, 대화 도메인

### spec-01-10 — 노트로 정리

- **요점**: (선택 단계) 달라진 생각을 내 손으로 적어 남긴다. 토론을 하지 않아도 쓸 수 있다.
- **방향성**: 노트는 "처음 해석"(자동으로 붙음), "달라진 점"(내가 씀), "모임 기록"(AI 가 정리, AI 가 쓴 것으로 표시)으로 이루어진다. AI 는 내 글의 초안을 쓰지 않는다. "달라진 점"은 짧아도 되고 "달라지지 않았다"도 허용한다.
- **참조**:
  - `docs/goals.md` §핵심 경험 6, §원칙 "내 글과 AI 글을 섞지 않는다"
- **연관 모듈**: 노트 도메인

## 🧪 통합 테스트 시나리오 (간결)

> 본 phase 의 Done 조건 중 하나. 구현 위치와 실행 명령은 spec-01-03 에서 확정합니다.

### 시나리오 1: 책 한 권의 전체 흐름
- **Given**: 빈 데이터베이스와 실행 중인 로컬 환경 (LLM 과 웹 검색은 테스트용 대역 사용)
- **When**: 책을 등록하고, 내 해석을 저장하고, 배경과 다른 시선과 비교를 본다 (선택 단계를 만든 경우 토론과 노트까지)
- **Then**: 각 단계의 결과가 저장되어 있고, 환경을 재시작한 뒤에도 모두 조회된다
- **연관 SPEC**: spec-01-04 ~ spec-01-10

### 시나리오 2: 먼저 쓰고, 그다음 본다
- **Given**: 책은 등록했지만 내 해석을 저장하지 않은 상태
- **When**: 다른 시선과 비교를 화면과 API 로 요청한다
- **Then**: 두 경로 모두 거부된다. 독자 단위 작업(연결, 비교)은 만들어지지 않는다. 책 단위 자료 수집은 뒤에서 진행될 수 있지만 그 결과와 개수는 내주지 않는다 (ADR-004 §7)
- **연관 SPEC**: spec-01-05, spec-01-08

### 시나리오 3: 출처 없는 사실과 시선은 표시하지 않는다
- **Given**: 웹 검색 결과가 비어 있거나, 인용 문장이 가져온 본문에 없도록 설정한 테스트 대역
- **When**: 배경과 다른 시선을 요청한다
- **Then**: 배경은 사실로 단정한 문장 없이 "확인하지 못함"으로 표시되고, 시선은 실제 사람의 것으로 표시된 항목 없이 AI 가 만든 해석만 그 표시와 함께 나온다
- **연관 SPEC**: spec-01-06, spec-01-07, spec-01-08

### 시나리오 4: 글쓴이 구분이 유지된다 (선택 단계를 만든 경우)
- **Given**: 토론까지 마친 모임
- **When**: 노트를 저장하고 다시 조회한다
- **Then**: "달라진 점"은 내가 쓴 것으로, "모임 기록"은 AI 가 쓴 것으로 구분되어 저장되어 있다
- **연관 SPEC**: spec-01-09, spec-01-10

### 통합 테스트 실행
```bash
docker compose up -d --wait db   # 테스트용 DB
pnpm test                         # 단위·통합 테스트 (inkle_test 데이터베이스 사용)
```

시나리오별 테스트는 각 spec 에서 `src/**/*.test.ts` 로 추가한다.
