## 배경 및 문제 정의

### 현재 상황

수동 실험(spec-01-01)으로 흐름을 확인했고 점검 1 은 "계속"이다. 저장소에는 문서만 있고 확정된 아키텍처가 없다. 워킹트리에는 커밋하지 않은 Next.js 뼈대가 남아 있다 (Next.js 16, React 19, `postgres`, `@anthropic-ai/sdk`, `zod`, Tailwind).

### 문제점

구현을 시작하려면 아래가 정해져 있어야 한다. 정하지 않고 시작하면 spec-01-04 이후에 저장 구조를 다시 뜯게 된다.

- 실험에서 드러난 제약이 구조에 반영되어야 한다. 출처 검증은 필수이고, 자료 수집은 느리고 비싸며, 배경과 시선은 책 단위로 재사용해야 한다 (`docs/experiments/01-manual-flow/findings.md` §spec-01-02 로 넘길 입력).
- "먼저 쓰고, 그다음 본다"를 서버에서 강제해야 한다 (phase-01 성공 기준 5).
- 이후 단계(개인 위키, 커뮤니티)가 지금 저장하는 자료를 그대로 쓸 수 있어야 한다.

### 해결 방안

다섯 가지 결정을 각각 선택지와 근거를 비교해 ADR 로 남긴다. 코드는 쓰지 않는다. ADR 이 확정되면 phase-01 의 이후 spec 범위와 순서를 다시 검토한다.

## 요구사항

1. ADR 5개를 `docs/decisions/` 에 kit 양식으로 작성한다. 각 ADR 은 선택지 2개 이상과 채택하지 않은 이유를 담는다.
2. `findings.md` 의 입력 9개가 각각 어느 ADR 에서 다뤄졌는지 추적할 수 있다.
3. `docs/goals.md` 의 원칙 9개와 어긋나는 결정이 없다.
4. 확인하지 못한 가정은 ADR 안에 "검증이 필요한 가정"으로 적고, 어느 spec 에서 확인할지 정한다.
5. ADR 결과를 `backlog/phase-01.md` 에 반영한다 (이후 spec 의 범위와 순서, 미커밋 뼈대의 처리).
6. Claude Code CLI 의 구체적인 사용법(비대화 실행, 출력 형식, 컨테이너 안에서의 로그인)은 기억이 아니라 공식 문서를 확인해 적는다.
7. LLM 을 부르는 곳은 하나의 경계 뒤에 둔다. 지금은 Claude Code CLI 로 채우고, 나중에 Claude API 로 바꿀 때 그 경계 안쪽만 고치면 되어야 한다.

## 🛑 사용자 검토 필요

아래는 ADR 에 적을 제안이다. Plan Accept 는 "이 방향으로 ADR 을 작성해도 좋다"는 뜻이고, 각 ADR 의 최종 확정은 PR 검토에서 한다.

> [!IMPORTANT]
> - [ ] **스택: Next.js 단일 웹 앱 (TypeScript) + Postgres + docker compose.** 워킹트리의 뼈대를 살린다. 대안은 프론트와 Python 백엔드 분리다.
> - [ ] **LLM 은 Claude Code CLI 로 부른다** (사용자 제안, 2026-11-17). 작업 프로세스가 `claude -p` 를 비대화 방식으로 실행하고 구독 한도 안에서 쓴다. API 키와 사용량 과금은 나중으로 미룬다. 구독은 본인 사용에만 쓸 수 있으므로, 다른 사람에게 서비스를 열기 전에는 Claude API 로 바꿔야 한다.
> - [ ] **페이지는 앱이 직접 가져온다.** CLI 의 웹 가져오기는 페이지 원문이 아니라 요약을 돌려주므로 문장 대조에 쓸 수 없다. AI 는 검색과 인용 후보 추출만 하고, 작업 프로세스가 주소를 직접 열어 본문을 받는다.
> - [ ] **자료 수집용 작업 프로세스를 따로 둔다.** 웹 앱과 같은 코드, 같은 이미지에서 뜨는 두 번째 컨테이너다. 수집이 분 단위로 걸려 웹 요청 안에서 처리할 수 없다.
> - [ ] **인용 검증은 코드로 한다.** AI 가 "출처에 있다"고 말하는 것을 믿지 않고, 인용 문장이 가져온 페이지 본문에 실제로 들어 있는지 문자열로 대조한다. 대조에 실패한 내용은 보여주지 않는다. 그 결과 보여줄 자료가 줄어들 수 있다.

> [!WARNING]
> - [ ] **검증이 필요한 가정**: docker 컨테이너 안에서 CLI 가 구독 로그인으로 동작하는가. macOS 에서는 로그인 정보가 키체인에 있어 컨테이너가 읽지 못한다. 장기 토큰을 환경 변수로 넘기는 방법이 있는지 ADR-004 작성 때 공식 문서로 확인하고, spec-01-03 에서 가장 먼저 실제로 돌려 본다. 안 되면 작업 프로세스만 컨테이너 밖(호스트)에서 띄운다.
> - [ ] **CLI 방식의 한계**: 구독 사용량 한도에 걸리면 수집이 멈춘다. API 보다 호출이 느리다. 출력 형식을 강제하기 어려워 받은 결과를 코드로 검사하고, 형식이 틀리면 다시 시도해야 한다.

## 핵심 전략

각 ADR 의 제안 방향. 상세한 선택지 비교는 ADR 본문에 쓴다.

| ADR | 제안 | 이유 |
|:---:|:---|:---|
| **001 앱 구조와 스택** | Next.js 단일 앱. 화면은 서버의 HTTP API 만 통해 자료를 읽는다. 작업 프로세스는 같은 코드에서 별도 컨테이너로 뜬다. 작업 대기열은 Postgres 테이블 | 혼자 만들고 언어가 하나다. API 를 경계로 두면 나중에 모바일 앱이 붙을 수 있다. 대기열 전용 서비스를 추가하지 않는다 |
| **002 데이터 모델** | 자료를 두 층으로 나눈다. **책 단위**: 책, 출처, 배경 항목, 시선. **독자 단위**: 모임, 내 해석, 내 해석과의 연결, 비교, 끝의 한 번 고르기. 시선은 종류(외부 사람 / AI / 이후 inkle 독자)를 가진 하나의 개념이고 "얼마나 흔한 읽기인가"를 갖는다. 글로 된 모든 자료에 글쓴이(나 / AI / 외부 사람)를 남긴다. 장르는 책의 속성이다 | 입력 3, 5, 7, 8. 책 단위 층은 3단계 책별 공유 위키로 이어진다 |
| **003 사용자 식별** | 독자 단위 자료에는 처음부터 사용자 식별자를 둔다. 지금은 로컬 사용자 한 명을 미리 만들어 쓰고 인증은 없다 | 나중에 넣으면 모든 테이블을 고쳐야 한다. 책 단위 자료는 사용자에 묶지 않는다 |
| **004 LLM 근거와 출처 검증** | LLM 호출은 하나의 경계 뒤에 두고 지금은 Claude Code CLI 로 채운다. AI 가 검색해 주소와 인용 후보를 내고 → 작업 프로세스가 페이지를 직접 가져오고 → 코드가 문장을 대조하는 세 단계. 출처마다 종류(직접 인용 / 기자나 편집자의 정리 / 재인용 / 요약만 확인)를, 오독 지적마다 근거의 종류(출처 확인 / 모델의 기억)를 저장한다. 수집은 내 해석을 쓰는 동안 미리 시작할 수 있지만, 결과는 해석이 저장된 뒤에만 API 가 내준다 | 입력 1, 2, 4, 6, 9. 실험에서 검색 요약 7개 중 2개가 원문과 달랐다 |
| **005 원본과 파생물** | 원본(내 해석, 토론 대화, 노트, 가져온 출처 본문의 인용 부분)은 고치지 않고 덧붙이기만 한다. 파생물(연결, 비교, 이후 위키)은 어떤 원본과 어떤 모델·프롬프트 판에서 만들어졌는지를 남겨 다시 만들 수 있게 한다 | 원칙 "원본을 보존한다". 프롬프트를 고친 뒤 과거 모임을 다시 만들 수 있다 |
