# ADR-003: 독자 단위 자료에는 처음부터 사용자 식별자를 둔다

## 📚 Context

- 1단계는 만든 사람 혼자 로컬에서 쓰고 인증이 없다 (`backlog/phase-01.md` 결정 기록).
- 3단계에서 여러 사용자가 쓰고, 원칙 "개인 데이터는 기본 비공개"를 지켜야 한다 (`docs/goals.md`).
- ADR-002 가 자료를 책 단위와 독자 단위로 나눴다.

## 🎯 Decision

1. **독자 단위 자료(모임, 내 해석, 연결, 비교, 끝의 한 번 고르기, 토론, 노트)는 사용자 식별자를 가진다.** 모임이 사용자를 가리키고, 나머지는 모임을 통해 사용자에 묶인다.
2. **책 단위 자료(책, 출처, 배경 항목, 시선)는 사용자에 묶지 않는다.**
3. **지금은 로컬 사용자 한 명을 DB 에 미리 만들어 둔다.** 로그인 화면과 인증은 만들지 않는다. 모든 요청은 이 사용자의 것으로 처리한다.
4. **"지금 사용자가 누구인가"를 정하는 코드는 한 곳에 둔다.** 도메인 모듈의 독자 단위 함수는 사용자 식별자를 인자로 받고, 다른 사용자의 자료는 내주지 않는다. 인증을 붙일 때는 그 한 곳만 바꾼다.

## 📊 Consequences

- **긍정**: 인증을 붙일 때 테이블을 고치거나 기존 자료를 옮길 필요가 없다.
- **긍정**: "다른 사용자의 자료는 보이지 않는다"를 지금부터 테스트로 확인할 수 있다 (테스트에서 사용자를 둘 만들면 된다).
- **부정**: 혼자 쓰는 동안에는 쓰이지 않는 인자가 모든 독자 단위 함수에 붙는다.
- **중립**: 책을 누가 등록했는지는 기록하지 않는다. 책은 공유 자료다. 3단계에서 책 등록에 검토 절차가 필요한지는 그때 정한다.

## 🔀 Alternatives

- **인증을 붙일 때 식별자를 추가**: 지금 코드가 가장 단순하다 — 비채택 이유: 모든 독자 단위 테이블과 조회를 고쳐야 하고, 그때까지 쌓인 자료를 옮겨야 한다. 지금 넣는 비용은 컬럼 하나와 인자 하나다.
- **지금 인증까지 구현**: 3단계 준비가 끝난다 — 비채택 이유: 혼자 로컬에서 쓰는 단계에 필요가 없고, 호스팅 방식이 정해지지 않아 어떤 인증을 쓸지 고를 근거가 없다.
- **책 단위 자료에도 사용자 식별자를 둠** (사용자별 책 목록): 사용자마다 자기 책을 관리한다 — 비채택 이유: ADR-002 의 재사용이 깨지고, 서재 관리는 하지 않기로 했다 (`docs/goals.md` §하지 않을 것).
