# ADR-001: 단일 Next.js 앱과 별도 작업 프로세스로 만든다

## 📚 Context

- 만드는 사람은 한 명이고, 1단계는 본인이 로컬 docker 환경에서 쓴다 (`backlog/phase-01.md`).
- 배경과 다른 시선을 모으는 데 수십 초에서 분 단위가 걸린다 (`docs/experiments/01-manual-flow/findings.md` 입력 4). 웹 요청 하나 안에서 끝낼 수 없다.
- "내 해석을 저장하기 전에는 다른 시선과 비교가 화면과 API 어디에서도 나오지 않는다"를 자동 테스트로 검증해야 한다 (phase-01 성공 기준 5).
- 사업화 시점에 모바일 앱이 필요할 수 있다 (`docs/goals.md` §열린 질문). 지금은 웹만 만든다.
- 워킹트리에 커밋하지 않은 Next.js 16 뼈대가 있다 (TypeScript, React 19, Tailwind, `postgres`, `zod`).

## 🎯 Decision

1. **단일 웹 앱**: Next.js(App Router)와 TypeScript 로 화면과 서버를 한 프로젝트에 둔다. 저장소는 Postgres 다.
2. **컨테이너 셋**: `docker compose` 로 웹 앱, 작업 프로세스, DB 를 띄운다. 작업 프로세스는 웹 앱과 같은 코드와 같은 이미지에서 시작 명령만 다르게 뜬다.
   - 고침 (2026-11-17, spec-01-03): 지금은 작업 프로세스를 호스트에서 띄운다. CLI 의 구독 토큰을 쓰지 않고 이 기기의 로그인을 쓰기로 했기 때문이다 (ADR-004 §가정의 확인 결과). `docker compose` 는 웹 앱과 DB 를 띄우고, 작업 프로세스는 같은 코드를 호스트에서 실행한다.
3. **작업 대기열은 Postgres 테이블**이다. 웹 앱이 작업을 넣고, 작업 프로세스가 가져가 처리하고 상태를 적는다. 화면은 작업 상태를 주기적으로 물어 진행 상황을 보여준다.
4. **자료 접근의 경계는 둘이다.**
   - 도메인 모듈: DB 를 읽고 쓰는 코드는 모두 여기에 둔다. "내 해석 저장 전에는 내주지 않는다" 같은 규칙을 이 층에서 강제한다.
   - HTTP API: 화면은 HTTP API 로만 자료를 읽고 쓴다. 화면 코드에서 DB 나 도메인 모듈을 직접 부르지 않는다.
5. **모바일 앱에 대한 가정**: 1~2단계는 반응형 웹만 만든다. 모바일 앱이 필요해지면 같은 HTTP API 를 쓰는 별도 클라이언트로 붙인다. 그때 필요한 것은 인증과 API 의 버전 관리이고, 지금은 만들지 않는다.
6. **미커밋 뼈대는 살린다.** spec-01-03 에서 정리해 커밋한다. `@anthropic-ai/sdk` 의존성은 ADR-004 에 따라 뺀다.

ORM 사용 여부, 테스트 실행기, 마이그레이션 도구는 이 결정의 범위가 아니다. spec-01-03 에서 정한다.

## 📊 Consequences

- **긍정**: 언어와 빌드가 하나다. 타입을 화면과 서버가 공유한다.
- **긍정**: 대기열 전용 서비스(Redis 등)가 없어 컨테이너와 운영 지식이 늘지 않는다. 작업 기록이 DB 에 남아 실패 원인을 SQL 로 볼 수 있다.
- **긍정**: 노출 규칙을 강제하는 곳이 도메인 모듈 하나라, 성공 기준 5 를 그 층과 HTTP API 두 곳의 테스트로 검증할 수 있다.
- **부정**: 화면이 HTTP API 만 쓰게 하면 Next.js 의 서버 컴포넌트에서 자료를 바로 읽는 편리함을 포기한다. API 경로와 호출 코드를 한 번 더 써야 한다.
- **부정**: Postgres 대기열은 작업이 많아지면 한계가 있다. 혼자 쓰는 단계에서는 문제가 되지 않고, 3단계 전에 다시 본다.
- **부정**: 작업 프로세스가 웹 앱과 같은 이미지를 쓰므로 이미지에 작업용 도구(ADR-004 의 CLI)가 함께 들어간다.
- **중립**: 진행 상황은 주기적 조회로 보여준다. 토론(spec-01-12, 2026-11-20 번호 고침)의 스트리밍 응답은 그 spec 에서 따로 정한다.

## 🔀 Alternatives

- **프론트와 Python 백엔드 분리** (React + FastAPI): 텍스트 처리 라이브러리는 Python 쪽이 풍부하다 — 비채택 이유: 언어와 빌드가 둘이 되고 타입을 공유하지 못한다. 이 제품의 텍스트 처리는 문자열 대조 수준이라 Python 의 이점이 작다.
- **Next.js 서버 액션과 서버 컴포넌트만 쓰고 HTTP API 를 두지 않음**: 코드가 가장 적다 — 비채택 이유: 화면 밖에서 부를 수 있는 경계가 없어 모바일 클라이언트를 붙이려면 다시 만들어야 하고, "API 에서도 나오지 않는다"를 검증할 대상이 없다.
- **작업 프로세스 없이 웹 요청 안에서 수집**: 컨테이너가 하나 줄어든다 — 비채택 이유: 분 단위 작업이라 요청이 끊기면 결과를 잃고, 내 해석을 쓰는 동안 미리 시작할 수 없다.
- **대기열 전용 서비스** (Redis 기반 등): 재시도와 동시 처리 기능이 갖춰져 있다 — 비채택 이유: 혼자 쓰는 단계에 서비스 하나를 더 운영할 이유가 없다.

## 📌 Status

일부 대체 (2026-11-17): §1 의 "화면과 서버를 한 프로젝트에"와 §2 의 컨테이너 구성은 ADR-009 가 대체한다. API 는 Next.js 와 다른 서버(`apps/api/` (진입점)와 `packages/backend/src/server/` (서버 생성))로 뜨고, compose 는 web · api · db 다. 같은 저장소, 같은 이미지라는 점은 그대로다.


Accepted (2026-11-17, spec-01-02, PR #2 병합). 첫 적용: spec-01-03 프로젝트 뼈대.
